# Локальное хранение, медиа и переносимые резервные копии

## Решение

Для iOS и Android принять `expo-sqlite` как единственный источник истины
пользовательских данных, `expo-file-system` как хранилище неизменяемых
изображений и собственный версионируемый ZIP-архив для экспорта/импорта.
Это решение рассчитано на согласованный в #3 стек Expo prebuild/Dev Client,
React Native 0.80+ и New Architecture.

`react-native-mmkv`, выбранный в #3 для MVP CRUD, оставить только для
некритичных настроек интерфейса (например, тема или факт показа подсказки).
Он не подходит для набора карточек, который требуется целиком и
согласованно заменить из архива: у него нет реляционной модели, SQL-миграций
и транзакции, объединяющей несколько записей. Изменение относительно #3
преднамеренно: у #16 более сильные требования — собственный переносимый
бэкап с фотографиями и безопасное восстановление.

Не поддерживать формат JSON существующей PWA и не экспортировать бинарный
файл SQLite: это независимый, документированный формат мобильного
приложения. Бинарный снимок БД не решает перенос медиа и слишком жёстко
связывает бэкап со схемой и реализацией SQLite.

## Целевая структура на устройстве

### Данные карточек

Открывать одну БД, например `discount-cards.db`, через `expo-sqlite`;
`SQLiteProvider` может выполнять миграции до рендера приложения. База
сохраняется между перезапусками и поддерживает iOS и Android. Минимальная
модель:

- `cards`: UUID, название, тип и значение кода, выбранный цвет, признак
  избранного, даты и версия записи;
- `card_media`: UUID карточки, UUID медиа, порядок и роль (`photo` или
  `custom-logo`);
- `media`: UUID, относительный путь, MIME-тип, размер, SHA-256 и даты;
- `schema_migrations`: применённая версия схемы;
- при необходимости `import_journal`: техническая запись незавершённого
  импорта для диагностики и уборки.

Каталожный бренд не является пользовательской записью: его стабильный ID,
название, цвет и bundled-логотип поставляются приложением. Карточка хранит
`catalogBrandId` **либо** собственное имя бренда. Для импорта неизвестный
`catalogBrandId` не должен ломать карточку: восстановить её как
произвольный бренд из экспортированного снимка имени и цвета; bundled-логотип
в этом случае отсутствует. Так обновление каталога не уничтожит данные
пользователя.

### Фото и логотипы

После выбора изображения немедленно скопировать его из URI камеры/галереи в
песочницу приложения; не хранить внешний или временный URI. Помещать файлы в
`Paths.document/media/<sha256>.<расширение>` (или UUID, если хеш вычисляется
после записи), а в SQLite — только относительный путь и метаданные. В
`Paths.document` файлы не считаются удаляемым системой кэшем; `Paths.cache`
предназначен для временных файлов и может быть очищен ОС.

Не дублировать bundled-логотипы каталога в медиа-каталоге и не включать их в
бэкап: они принадлежат версии приложения. Локальный логотип, добавленный
пользователем, — обычный объект `media` и экспортируется вместе с
фотографиями. Ограничить допустимые MIME-типы изображениями, нормализовать
расширение по проверенному содержимому и задать продуктовые лимиты числа
фото, размера одного файла и суммарного размера.

## Формат собственного бэкапа v1

Экспортировать один файл
`discount-cards-backup-v1-YYYY-MM-DD.zip` с MIME
`application/vnd.bnd.discount-cards-backup+zip`. Внутри:

```text
manifest.json
media/<sha256>.<extension>
```

`manifest.json` содержит как минимум:

- `format: "bnd.discount-cards.backup"`, `formatVersion: 1`,
  `createdAt`, идентификатор приложения и версию экспортёра;
- массив карточек, их связей с медиа и снимки произвольных/неизвестных
  брендов;
- для каждого медиа: путь без ведущего `/`, MIME-тип, размер и SHA-256;
- необязательные поля должны быть допускаемы будущими читателями, а
  неизвестные поля — игнорироваться после проверки версии формата.

Импорт принимает только этот MIME/расширение и `formatVersion`, для которого
в приложении есть мигратор. Новая версия формата не должна переопределять
семантику существующего поля; при несовместимой версии отказать до любых
изменений. Схема должна валидировать UUID, строки кода, перечисления,
максимальные размеры, число карточек и отсутствие повторяющихся ID/путей.
SHA-256 — контроль целостности в манифесте, а не механизм шифрования.

Для ZIP использовать нативный `react-native-zip-archive` v9: upstream
декларирует iOS 15.5+, Android API 23+ и RN 0.70+, совместимость с New
Architecture, а для Expo — Dev Build/EAS с config plugin, не Expo Go. Он
умеет заранее перечислить записи и сообщить их распакованный размер, а также
отклоняет небезопасный путь (`ERR_UNSAFE_PATH`). До внедрения закрепить
проверенную версию пакета и прогнать экспорт/импорт на реальных iOS и Android
с Expo prebuild. Если поддержка Expo Go становится обязательной, разумная,
но менее масштабируемая альтернатива — архив без ZIP, где JSON и каждое фото
пользователь явно экспортирует отдельно; JS ZIP для больших фотографий не
рекомендуется из-за памяти.

Для выбора архива использовать `expo-document-picker` с
`copyToCacheDirectory: true`: документация Expo предупреждает, что иначе
прочитать выбранный файл через FileSystem сразу удаётся не всегда. Готовый
временный ZIP положить в `Paths.cache` и передать локальный `file://` URI в
`expo-sharing`; на iOS/Android это поддерживается. Полная Share Extension для
входящего бэкапа не нужна в v1: достаточно явного экрана «Импорт».

## Атомарный и безопасный импорт

SQLite гарантирует атомарность **одной транзакции БД**, но не транзакцию,
одновременно охватывающую файловую систему и БД. Поэтому не заменять
пользовательский каталог файлов и БД «на месте». Алгоритм:

1. Приостановить операции изменения карточек и экспорт одним
   process-local mutex; попросить пользователя выбрать режим
   «заменить всё» либо «добавить как копии». Для v1 рекомендован только
   явный режим «заменить всё».
2. Скопировать выбранный архив в cache, проверить общий размер, список ZIP
   записей и запретить абсолютные пути, `..`, дубликаты и симлинки. Распаковать
   только в новый уникальный staging-каталог.
3. Прочитать и полностью провалидировать `manifest.json`; проверить каждый
   файл, его размер, MIME и SHA-256. Не открывать изображения декодером до
   лимитов. При любой ошибке удалить staging и не менять рабочие данные.
4. Скопировать проверенные файлы в постоянный каталог под новыми
   content-addressed именами. Файлы до коммита считаются сиротами и безопасны:
   рабочие строки БД на них ещё не ссылаются.
5. Выполнить `withExclusiveTransactionAsync`: создать/обновить все строки,
   связи и служебную запись импорта; при «заменить всё» удалить старые строки
   в той же транзакции. Использовать именно exclusive-вариант, поскольку
   обычная async-транзакция Expo допускает попадание посторонних запросов в её
   транзакцию.
6. Только после успешного коммита удалить старые неиспользуемые медиа и
   staging. При сбое до коммита остаётся прежняя БД; при сбое после него
   остаются только удаляемые сборщиком мусора сироты, но ни одна карточка не
   ссылается на отсутствующий файл.

Нельзя реализовывать восстановление удалением старых медиа до коммита или
простым перезаписыванием файлов: выключение приложения между этими шагами
даст битые ссылки. SQLite описывает атомарный commit как «все изменения
транзакции либо ни одного» и имеет журнал восстановления после сбоя питания;
это свойство и является границей атомарности дизайна.

Экспорт также выполняется под этим mutex: внутри read-транзакции получить
снимок строк и список медиа, скопировать их в уникальный staging-каталог,
записать манифест и создать ZIP. Отдавать файл через share sheet лишь после
успешного завершения ZIP. Ошибка создаёт только временные файлы, которые
можно удалить при следующем запуске.

## Безопасность и системные бэкапы

- Песочница приложения ограничивает доступ других приложений, но сама по себе
  не равна прикладному шифрованию. Не логировать коды карточек, JSON
  манифеста, URI или пароли архива; очищать staging и export-кэш после
  использования.
- Архив содержит предъявляемые коды и фотографии, поэтому перед шарингом
  явно предупредить пользователя, что обычный ZIP читается тем, кому он
  передан. Парольный ZIP не включать в v1 без отдельного решения о KDF,
  способе ввода и восстановлении пароля; «стандартное» ZIP-шифрование не
  следует выдавать за современную защиту. Для будущей защиты предпочесть
  проверенный AEAD-формат с памятьёмкой KDF, а не самодельную криптографию.
- SQLCipher в `expo-sqlite` — возможная отдельная защита БД at rest: Expo
  поддерживает его на iOS и Android, но для него нужны config plugin и
  `expo prebuild`, а Expo Go не поддерживается. Не включать его в #16 без
  проектирования хранения ключа (Keychain/Android Keystore), миграции
  существующей БД и восстановления при переустановке.
- Не считать Android Auto Backup реализацией функции экспорта. По умолчанию
  он включает большую часть файлов приложения и БД, работает при подходящих
  условиях приблизительно раз в сутки и ограничен 25 MB на приложение.
  Медиа легко превысят лимит. Для релиза явно выбрать privacy-политику:
  рекомендовано исключить `database` и каталог `media` из Android Auto Backup
  и предоставлять только явный пользовательский экспорт; если продукт
  разрешит системный бэкап, описать включения/исключения и квоту в Android
  backup rules. На iOS также явно пометить рабочий медиа-каталог как
  исключённый из системного backup, если выбран режим «только явный экспорт».

## Рассмотренные варианты

1. **MMKV + FileSystem + JSON.** Хорош для небольших preferences и был
   оправдан как узкий MVP в #3. Не рекомендуется: нет транзакционной замены
   набора карточек и устойчивой эволюции сложной модели.
2. **SQLite + FileSystem + наш ZIP (рекомендуется).** Даёт миграции,
   связи карточка—медиа, атомарную замену метаданных и один файл для
   пользователя. Цена — схема БД, миграции и один нативный ZIP-модуль.
3. **SQLite с BLOB-изображениями.** Отвергнут: раздувает БД, усложняет
   выборочную очистку, просмотр и экспорт; нет выгоды для фотографий
   карточек.
4. **Системные iCloud/Android Auto Backup вместо экспорта.** Отвергнут как
   основной путь: пользователь не получает переносимый файл и не управляет
   моментом/содержимым; Android ограничивает объём 25 MB.
